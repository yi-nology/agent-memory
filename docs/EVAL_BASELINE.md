# 召回质量基线（v0.7.x）

本文记的是**可复现的一组数字**：同一份数据、同一条召回链、同一套口径，
跑出来的结果。任何人改动召回链之后，都能拿它对比。

复现命令：

```bash
go test ./integration/ -run TestRecallBaseline -v
```

## 数据集

`evaluation.NewSynthetic(20261021, 40)` —— 40 条用例、每条 8 张合成事实卡：

- **相关** 2~3 条，与查询共享的词数逐条递减（3 / 2 / 1）；
- **近义干扰** 2 条（共享 2 个词、换一个词）；
- **无关** 3 条（一个词都不共享）；
- **越权陷阱** 1 条（词面完美但归属属于别的读者）。

同 seed 必得同结果（私持随机源，不碰全局 `rand`）。

## 三套口径的数字（本机实测）

| 口径 | 指标 | 实测 |
|---|---|---|
| 检索 | Recall@1 / @3 / @5 / @10 | 0.404 / 0.646 / 0.646 / 0.646 |
| 检索 | nDCG@5 / MRR / HitRate | 0.699 / 1.000 / 1.000 |
| 问答 | 上下文充分率 | 0.300 |
| 问答 | 答对率 | 未测（本仓不配回答器与判分器——那是宿主的能力） |
| token 效率 | 每次查询平均 token | 527.8 |
| token 效率 | 每千 token 命中条数 | 2.984 |
| token 效率 | 每命中一条的 token | 335.1 |

**这组数字是加了「宽松词面路」之后的结果**（见下节「宽松路带来的变化」）。

「已测 / 未测」是分开的：答对率**未测**而不是 0（没配判分器就不给数），
token 效率有 `Measured` 标志（召回器报不出 token 时不冒充 0）。

## 这组数字暴露了什么（以及怎么修的）

**1. 词面路是隐式 AND，于是「多话题查询」几乎打不中。**

`store.FTS5Query` 的语义是「空格连接即隐式 AND」——
查询的每个词都必须在正文里出现才算命中。
所以一条查询若有三个词，只有**三个词全中**的事实进了检索路；
共享两个词、一个词的那些，全靠「高价值兜底」那一路
（按重要度/新鲜度取，**与查询无关**）——
而一旦语料稍大，兜底那一路取回的是**同一批**全局重要事实，
与这条查询无关。

数字上的表现（**修之前**）：Recall@3 之后**不再上升**（0.533 → 0.533 → 0.533），
而 Recall@1 只有 0.404 —— 说明「每条查询都能找到完全匹配的那一条」
（HitRate=1.0、MRR=1.0），但**部分匹配的事实进不来**。

**2. 上下文充分率（修之前只有 0.025）—— 一次查询给不出答一道多事实问题的上下文。**

充分的口径是「支撑事实**全部**在上下文里」。每条用例有 2~3 条支撑事实，
而 Recall@5 只有 0.53 ⇒ 几乎不可能凑齐 ⇒ 充分率极低。

这条数字是本仓与「同等准确率下少花 token」那类叙事的差距所在：
我们的准确率（HitRate/MRR）不差，但**可用的上下文**不够。

**3. 每命中一条（修之前 372.6 token）。**

这个数看起来不小，但它衡量的是「词面 AND + 重要度兜底」这套取数方式：
要么全中（准），要么什么都捞不到相关（只剩全局重要事实），
中间那档（部分匹配）根本没进池。

## 宽松路带来的变化（已修）

修法：**加一条「宽松匹配」的路**（命中任一词），把它当成**第三路**喂给 RRF 融合——
全中的那条在严格路与宽松路**都出现**（融合分最高），部分匹配的那些从宽松路进来。
这比把 AND 改成 OR 好：OR 会把噪声一次性灌进池子。

| 指标 | 修之前 | 修之后 | 变化 |
|---|---|---|---|
| Recall@3 / @5 | 0.533 | **0.646** | +21% |
| nDCG@5 | 0.631 | **0.699** | +11% |
| 上下文充分率 | 0.025 | **0.300** | **×12** |
| 每命中一条的 token | 372.6 | **335.1** | −10%（更便宜了） |

即：召回**更全**了（部分匹配的事实进得来），**上下文更够答**了（充分率 12 倍），
而**单位成本还降了**（噪声进池，但预算仍优先给高相关的那些）。

实现：`store.FTS5QueryAny`（检索词元契约钉子）+ `store.SearchAtomsLoose`
+ `pipeline/recall/hybrid.go` 的三路 RRF 融合。
⚠️ 放宽的是**词的匹配方式**，不是**可见性**：归属/时序过滤一条没少。

## 数字的适用范围（别过度解读）

- 这是**合成集**上的数字，衡量的是**词面召回**（相关标注按词面共享标）。
- 它**不衡量语义召回**：本仓自带的 `HashEmbedder` 只捕捉词面软匹配，
  语义那一路要用宿主注入的真模型 Embedder 才算数。
- 它**不是**与公开基准（LoCoMo / LongMemEval）可比的数字：
  那两个是**问答口径**（答案对不对），需要一层「检索结果 → 答案」的判分，
  而判分用的模型归宿主（`evaluation.Answerer` / `evaluation.Judge` 两个口已就位）。
- 想接公开基准时，本仓侧需要做的只有「把数据集适配成 `evaluation.QACase`」，
  口径与判分接口都已就位。
